Closures in Go

Publish date: 2026-01-29

Intro

Closures are a powerful and, in my opinion, underutilized feature in Go. Personally I love the combination of strong and static typing with functions begin a first-class citizens in the language. In this post I want to show example usages in Go standard library, some examples convinient from my perspective and finally discuss closures in APIs design.

Let's start with what a closure is. A closure is a function which can reference things from outside its body. Let's do the simplest example: 

// int -> (int -> int)
func adder(base int) func(int) int {
  return func(i int) int { return base + i }
}

func main() {
  add5 := adder(5)
  fmt.Println(add5(3)) // prints 8
}

In the example above we define a function adder which takes an integer base and returns a function which takes another integer and adds it to base. Function adder returns a closure which captures the variable base from its surrounding context - parent function parameter.

It's a toy example, but it shows how in Go we can return a function func(int) int as return type and that function can reference variable base from outside its body.

Classics

Let's take a look at some classic examples of closures in Go standard library.

sort.Slice

Probably the most known example is sort.Slice function with the following signature: 

func Slice(slice interface{}, less func(i, j int) bool)

It takes a slice of data (as empty interface) and a closure less which compares two elements in the slice by their indices. This way we can sort any slice of data by providing our own comparison logic. This fuction was in the standard library long before Go had generics. This is also an example why Go chose to not have generics from the beginning. With the built-in generic data containers like slices []T and maps map[K]V, we can use closures to provide custom logic for operations like sorting, filtering, and transforming data without needing to define new types or interfaces. It wasn't the replacement for generics, but a way to achieve similar goals before generics were introduced. 

sort.Slice(users, func(i, j int) bool {
  return users[i].Age < users[j].Age
})

As we can see in the above example, the caller provides how to sort the slice of users by providing a closure which compares two users by their age. The sort.Slice function doesn't even know that it was given a slice of users. It's an example how we can use closures, to delegate some logic to the caller, without forcing them to implement some interface or define a new type.

http.HandlerFunc

If you ever implemented a HTTP server in Go, you probably used http.HandleFunc function, to register new HTTP endpoints. It has the following signature: 
func HandleFunc(pattern string, handler func(ResponseWriter, *Request))

It takes a URL pattern and a closure handler which is called whenever a request matches the given pattern. This way we can define our HTTP handlers as closures, capturing any variables from the surrounding context. This is also a good example, to present that those closures can be methods. Let's consider the following example: 

import (
  "database/sql"
  "net/http"
)

type MyService struct {
  dbConn *sql.DB
}

func (ms *MyService) getUser() (User, error) {
  ...
}

func (ms *MyService) GetUserHandler(
  w http.ResponseWriter, r *http.Request,
) {
  user, uErr := ms.getUser()
  if uErr != nil {
      http.Error(w, "User not found", http.StatusNotFound)
      return
  }
  if err := encode(w, http.StatusOK, user); err != nil {
      http.Error(
          w, "cannot get user from DB", http.StatusInternalServerError,
      )
      return
  }
}

func main() {
  svc := &MyService{dbConn: initDBConnection()}
  http.HandleFunc("/user", svc.GetUserHandler)
  http.ListenAndServe(":8080", nil)
}

In the example above HTTP handler for getting user is defined as a method on a type which keeps a database connection. This is often more convenient, than using http.Handle function, which takes an http.Handler interface as a parameter. In the latter case we would need to define a new type which implements ServeHTTP method and then create an instance of that type to register the handler. In case of http.HandleFunc we can have multiple methods on the same type for multiple HTTP endpoints.

context

Package context is a Go standard library which:

[...] defines the Context type, which carries deadlines, cancellation signals, and other request-scoped values across API boundaries and between processes.

Let's consider the following sample program: 

package main

import (
  "context"
  "fmt"
  "math/rand"
  "time"
)

func genNumbers(ctx context.Context, delay time.Duration) {
  for {
    select {
    case <-ctx.Done():
        return
    default:
    }
    fmt.Println(rand.Intn(100))
    time.Sleep(delay)
  }
}

func main() {
  ctx, cancel := context.WithCancel(context.Background())
  go genNumbers(ctx, 300*time.Millisecond)

  var input string
  fmt.Scanln(&input)
  if input == "x" {
    cancel()
    fmt.Println("Stopped printing random numbers.")
  }
}

Function context.WithCancel creates a new context which can be cancelled by calling the returned cancel function (a closure really). In the program above we pass that context to the genNumbers function which prints random numbers every 300 milliseconds until the context is cancelled. We call cancel function when user input from stdin is "x". This is a very common pattern in Go in general, but here in particulary a good example how closures can be used to pack internal logic about sending a signal and doing a cleanup. For caller, it's very simple - they just got a function without any arguments and return values, just a "call" mechanism.
